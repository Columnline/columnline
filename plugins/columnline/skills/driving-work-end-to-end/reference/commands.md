# Everyday workflow handoffs

Read [the shared contract](system.md) and the current tenant/source context before any action. Use only discovered current tool schemas. Preserve exact work and revision identity and check real readback. A missing surface is a named exception; do not invoke unreleased adapters or manufacture evidence.

| Request | Action and boundary |
|---|---|
| Add this to intake | Capture/classify/deduplicate the source. Existing-work context stays on that item; simple questions go to Snapshot Questions. Internal intake is stopped. |
| Acknowledge it | The acknowledgment worker reads prior replies and records the existing owner commitment to a decision/short plan/full plan/fix/research by an approved date. A message is sent only within actual current authority; no duplicate acknowledgment or invented promise. |
| Put a plan together | Investigate and prepare an issue-linked short plan or client-safe Materials PDF. Reuse an existing project where relevant; never create/promote one automatically. Read comments/history. Preparation does not change delivery/acceptance state. |
| Hold it for review | Preserve the prepared revision for the named reviewer. A Draft/hold label is not a privacy guarantee; do not place private or withheld content in client-readable records. Use an actually private supported working draft when needed. |
| Deliver the plan | Human reviews and sends/presents the exact revision on the authorized source. Record actual recipient/thread/revision and receipt through a supported current control. Publication alone is not Plan Delivered. |
| They said yes | Read the exact response and delivered revision. Questions, conditional assent, checkpoint mentions and silence are not acceptance. Record only covered scope/checkpoints, retain existing owner and queue the work without starting build. |
| Ready for work | Accepted-queue worker recommends priority/cycle/start readiness; the responsible person agrees dates/capacity and actually picks it up. No automatic assignment or new promises. |
| Mark delivered | Verify the actual result, then prepare a delivery-acceptance package. Human sends it; creation/status alone is not the package receipt or final acceptance. Research can itself be the deliverable. |
| They accepted delivery | Record exact authorized acceptance; only that scope becomes Live/Complete. Pending-delivery feedback reopens the existing affected item with linked feedback; keep an already working Live parent Live and use a child ask/fix. |
| Review outcomes | Read evidence against original intent and prepare the later case study. Its acceptance is separate from delivery; no automatic Proven/retirement sweep. |
| Cancel or pause | Honor an explicit authorized decision on the exact work. Preserve history; no inferred cancellation, historical bulk changes or shutdown of a standing service from issue completion. |

## Notes, Questions and commitment dates

Website/app annotations keep their filed canonical issue and original source. Intake capture is separate from the acknowledgment handoff. Owner/path and builder-accepted dates must be actual decisions; an undated prior reply goes back to its owner for clarification, not a second guessed acknowledgment. Do not assign or rewrite linked engineer work to satisfy a warning.

Simple Questions follow [questions.md](questions.md): canonical Tasks fields, protected human Send where supported, otherwise human reply and source-qualified completion through the existing control. No automatic client answers, new issue or PDF for an answered quick question.

The Pipeline desk checks current real due/overdue commitments and calendar/timeline context only. Each issue's own promised decision/fix/plan date wins over a parent milestone. Unknown dates stay visible as unknown; do not silently shift deadlines. Working-day rules remain working days. Native completion SLAs do not define client acknowledgment windows.

## Supported-record checks

Read the current plan/issue and Materials revision before writing. The existing Your Plan creation action requires an existing project and can publish immediately; neither `hold_for_review` nor a later withdrawal prevents initial visibility. A request to prepare is not authorization to create/publish. Use the actual current editor/draft packet for an existing plan and preserve accepted revisions/unrelated fields. Never invent native-channel receipts, acceptance parameters, comment actions or relation enums to force a save.
